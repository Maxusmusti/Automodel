Orthogonal Subspace Fine-Tuning (OSFT) adapts a model to a new task while protecting what it already knows. For
each targeted weight `W`, OSFT computes an SVD once, freezes the top singular directions, and trains only the
remaining low-rank factors. Every update stays orthogonal to the frozen subspace, so new learning does not
overwrite the dominant directions that encode prior knowledge. No replay data, adapters, or per-task parameters
are needed: the exported checkpoint is a plain dense model.

OSFT is described in Nayak et al., "Sculpting Subspaces: Constrained Full Fine-Tuning in LLMs for Continual
Learning" (ICLR 2026).

## How It Works

For each target matrix `W` (shape `N x M`), with `k = floor(min(N, M) * (1 - unfreeze_rank_ratio))`:

```text
W = U S V^T                       (fp32 SVD, once, after the base checkpoint loads)
U_high, S_high, V_high            top-k singular triplets      -> frozen
U_low,  S_low,  V_low             remaining triplets           -> trainable
W_eff = U_high S_high V_high^T + U_low S_low V_low^T
```

Each optimizer step projects the trainable factors' gradients onto the orthogonal complement of the frozen
subspaces, and projects the factors themselves again after the step. The second projection matters: AdamW's
per-element scaling would otherwise rotate updates back into the frozen subspace.

Non-target parameters (embeddings, norms, the output head) remain trainable, as in full fine-tuning.

## Enable OSFT

Add an `osft` section to a fine-tuning recipe:

```yaml
model:
  _target_: nemo_automodel.NeMoAutoModelForCausalLM.from_pretrained
  pretrained_model_name_or_path: Qwen/Qwen3-8B
  torch_dtype: float32  # fp32 master weights and optimizer state; compute runs in bf16 under FSDP2

osft:
  _target_: nemo_automodel.components._peft.osft.OSFTConfig
  unfreeze_rank_ratio: 0.25
  target_modules: ["*.q_proj", "*.k_proj", "*.v_proj", "*.o_proj", "*.gate_proj", "*.up_proj", "*.down_proj"]
```

A complete recipe is available at `examples/llm_finetune/qwen/qwen3_8b_squad_osft.yaml`:

```bash
automodel examples/llm_finetune/qwen/qwen3_8b_squad_osft.yaml --nproc-per-node 8
```

### Options

| Field | Default | Description |
|---|---|---|
| `unfreeze_rank_ratio` | `0.25` | Fraction of each matrix's singular directions (the smallest) that stays trainable. Larger values learn more and protect less. |
| `target_modules` | q/k/v/o and gate/up/down projections | Wildcard patterns of dense linear layers to decompose. Models with fused projections need their own names, for example `["*.qkv_proj", "*.o_proj", "*.gate_up_proj", "*.down_proj"]` for Phi-3/Phi-4. |
| `exclude_modules` | `[]` | Wildcard patterns to exclude. Mutually exclusive with `target_modules`. |
| `forward_mode` | `auto` | `reconstruct` materializes `W_eff` and runs one dense GEMM; `factored` multiplies through the factors. `auto` picks the cheaper one per layer and per call from the layer shape and token count. |
| `project_gradients_before_clipping` | `true` | Project gradients before gradient-norm clipping, so the clipped norm is the norm of the update actually applied. |

<Note>
`unfreeze_rank_ratio` counts singular directions, not parameters. The trainable factors `U_low`, `S_low`,
and `V_low` hold `(N + M) * r + r` values for `r` unfrozen directions. With `0.25`, this is 30-50% of the targets'
parameter count depending on matrix shapes (50% for square matrices, 36% overall for Qwen3-8B).
</Note>

## Checkpoints

- **Resumable checkpoints** store the OSFT factors (`*.osft_*` keys) next to the merged dense weights. Resuming
  restores the factors exactly, together with the optimizer state.
- **Consolidated Hugging Face exports** (`checkpoint.save_consolidated: true`) contain only the merged dense
  weights under the original parameter names. They load directly with Transformers, vLLM, or another round of
  OSFT for the next task.

## Continual Learning Settings

For a sequence of tasks, run one OSFT round per task, each starting from the previous round's consolidated
export. Every round recomputes the SVD, so the frozen subspace grows to cover what earlier tasks added.

- **`unfreeze_rank_ratio`:** 0.1 to 0.2 protects prior knowledge well; 0.25 suits a single task. The paper's adaptive
  allocation freezes 80% of each matrix on average (ratio 0.2). Ratio 0.1 retained earlier tasks best in our
  reproduction.
- **Shared embeddings and output head:** when the tasks share an output vocabulary (labels, formats), freeze the
  input embeddings and the output head. They are outside OSFT's constraint and are the main path of interference
  between tasks:

```yaml
freeze_config:
  freeze_modules:
    - path: model.embed_tokens
    - path: lm_head
```

## Measured Results

Measured on 8x H100 80GB against [mini_trainer](https://github.com/Red-Hat-AI-Innovation-Team/mini_trainer), the
paper authors' reference implementation (with Liger kernels and flash-attn).

**Throughput and memory.** Qwen3-8B, 16k tokens per GPU, fp32 master weights, `unfreeze_rank_ratio: 0.25`:

| | Step time | Peak memory / GPU | Model + optimizer state / GPU | Startup to first step |
|---|---|---|---|---|
| mini_trainer OSFT | 4.72 s | 22.8 GB | 11.4 GB | 198 s |
| AutoModel OSFT | 3.96 s | 22.7 GB | 9.5 GB | 77 s |
| AutoModel full fine-tuning | 3.30 s | 25.8 GB | 12.4 GB | |

- **Across 12 models from 9 families** (Llama, Qwen2/2.5/3, Mistral, Gemma2/3, Granite, OLMo2, Phi-4):
  - AutoModel OSFT runs 1.1-2.2x faster than mini_trainer.
  - Peak memory is equal or lower on 11 of 12 models.
  - Startup is 2-2.5x faster on all 12.
  - Gemma models need `attn_implementation: flash_attention_2` to get this speed.
- **Model and optimizer state per GPU** is below full fine-tuning's for `unfreeze_rank_ratio` up to about 0.5.
- **Step time** is about 1.2x full fine-tuning's. The projections take about 0.25 s per step.

**Quality.** Same data and evaluation for both implementations:
- **Single task:** held-out task loss and WikiText-2 retention are equal to mini_trainer's on all 12 models.
- **Paper benchmarks** with the continual-learning settings above (`unfreeze_rank_ratio: 0.1`, embeddings and output
  head frozen), one configuration for every result:
  - **Standard continual-learning benchmark, LLaMA-2-7B, 3 task orders:** average accuracy 79.5, against the
    paper's 79.6.
  - **TRACE, LLaMA-2-7B-Chat, 8 tasks:** average accuracy 55.1 with backward transfer -2.2, against the paper's
    48.4 / -7.1.
  - **General ability after all 8 TRACE tasks:** MMLU 46.8, BBH 40.4, PIQA 77.7 and BoolQ 82.3 are at or above the
    base model's 47.2, 40.1, 76.3 and 80.6 under the same evaluation.

## Tests

- **Unit tests (CPU):** forward paths against dense, gradient and parameter projection invariants, SVD exactness,
  state-dict load and export (including base loads that echo the factors), and autocast.
- **FSDP2 equivalence (2 ranks):** two optimizer steps against a single-process fp32 reference. The grid covers
  gradient accumulation, both clipping orders, and activation checkpointing.
- **Determinism:** the backward is bit-identical across runs on CUDA in bf16.
- **Functional test (L2, 2 GPUs):** training, the resumable checkpoint, the bitwise-identical next update after
  resume, and the Hugging Face export.
- **Checkpoint robustness:** the example recipe runs AutoModel's robustness phases 0-4.

## Limits

OSFT currently supports FSDP2 (and single-device) data parallelism. It raises an error when combined with PEFT,
quantization, FP8, QAT, or tensor, pipeline, or expert parallelism. Target modules must be dense linear layers
(`torch.nn.Linear` or Transformer Engine `Linear`); MoE expert weights are not decomposed. Ranks are allocated
uniformly by `unfreeze_rank_ratio`; the paper's adaptive per-layer allocation is not implemented.
